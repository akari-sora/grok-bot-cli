## What the Hermes test actually runs

The CI job downloads three official source files from `NousResearch/hermes-official-plugins`, pinned to commit `13b2c1c9c8204bf333df240b2aacf98c3e6250b7`. Each file must match the independently inspected Git blob ID before it is imported. Download, integrity or execution failure fails the required job; none is skipped. No mocked parser or copied simplified schema is substituted.

The fixture is generated by this branch's real `destinationFiles` converter: two same-named source bots, two role skills and two workflows with repeated source workflow IDs, plus non-ASCII text. The official importer is run in a temporary, isolated home as the unprivileged CI user.

Actual checks:

1. Official `parse_export` accepts the generated version-1 bundle, retains four distinct skill IDs and sees empty persona/memory/routine/app fields.
2. Official `GrokBotImporter(..., execute=False).run()` creates no target directory.
3. Official execute mode writes four real `skills/grok-bot-imports/*/SKILL.md` files containing the expected instructions, while seeded SOUL.md, config.yaml, MEMORY.md and USER.md remain byte-identical.
4. Running the same import again preserves every existing target file byte-for-byte; no duplicate skills or overwrite.

This establishes compatibility with the pinned official parser and local file importer for the tested role/skill mapping. It does not prove behavior in a running Hermes agent, compatibility with every installed version, a model's use of every instruction, or full account migration. The product itself downloads nothing; only the test downloads pinned official source.

## Multi-target and Trinity checks

The compiled public CLI executes `targets` and plan/apply/verify for OpenClaw, Hermes, Muse, dot and portable archives with no source credentials. All targets preserve the original source archive. Target-identity tampering is refused. Existing OpenClaw output conversion and its five-field v1 manifest are unchanged.

Muse/dot tests reconstruct long Chinese/emoji content from every ordered fragment, check each fragment and whole-payload digest, preserve exact source text, require explicit workflow-body inclusion, and verify deterministic safe paths. No generated auto-send script, network call, subprocess or remote account access exists in the converter.

The existing Trinity source was inspected rather than assumed: `ask` can accept top-level stdin, whereas `hand` forwards one previous message and `brief push` cannot write Muse instructions. Muse memory is read-only in the current CLI. The Muse adapter ultimately places message content in child-process argv, and uncertain sends must not be blindly repeated. These limits are documented in generated reports and usage docs. Trinity remains optional reviewed delivery, not an archive or Hermes dependency; no Trinity code changes or remote sends were performed.
